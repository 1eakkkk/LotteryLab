形态诊断：看看你的号码落在多大的一堆里

这一节的输入框已经合并到下方「号码工具」了——整页只留一个输入框，一次输入同时给出形态诊断与历史对照两份结果。这里先说明它背后的算法与读法。

给定任意 6 个红球，它会给出奇偶比、大小比、三区分布、连号情况和和值，并且——关键是最后一列——告诉你有多少组号码和它"长得一样"。这一列的数值由 C(33,6) 全部枚举算出来（1,107,568 组），不是查表抄来的。

把这一层读对，只需要看懂最后一列。它的意思是"全部 1,107,568 组红球里，有多少组和这组长得一样"——不是"这组号码中奖的机会有多大"。这两个数字完全不是一回事。

形态稀有只说明这组号码"长得比较特别"，不说明它更容易或更不容易被开出来。相反的方向才是真相：形态越"普通"（比如奇偶均衡、三区均匀），符合它的组合数越多——也就是说越是"看起来正常"的形态，同时选中它的人越多，万一真中了一等奖，还要和别人分。当然，这个影响小到可以忽略，因为中一等奖本身就是 1/17,721,088 的事。

本区块所有统计量都在构建期算好、写死在页面里（src/number-health.js，Node 与浏览器共用同一份公式），浏览器端只做查表与展示，不重算。这一点是刻意的：如果两端各算一套，页面上早晚会出现两个对不上的数字。

预测悖论：就算你真有"预测能力"，期望仍然是负的

这是本站最重要的一块内容，也是唯一一块不依赖任何历史数据、只靠数学就成立的结论。

第一步：单注的期望回报是多少？把每一档奖级的"概率 × 奖金"加起来。一、二等奖是浮动奖金（取决于当期奖池和中奖注数），这里给出低、中两档公开常见区间的估算——估算假设本身也写在数据里，不藏：

口径单注期望回报单注成本每投入 2 元，平均拿回
只算固定奖级（三~六等奖，金额是官方固定值）0.4863 元2 元24.3%
含浮动奖级（低档估算：一等奖 3,000,000 元）0.7402 元2 元37.0%
含浮动奖级（中档估算：一等奖 6,000,000 元）0.9942 元2 元49.7%

第二步：那"多买几注"能解决吗？不能，因为期望是线性的。想要靠"每期买若干注"把期望回报凑到 100 元，按不同估算口径需要：

  • 低档估算：每期约 135 注，每期投入 270 元，而这些注的期望回报正好是 100 元——依然是亏的，而且亏损比例和只买 1 注时完全相同；
  • 中档估算：每期约 101 注，每期投入 202 元，期望回报同样是 100 元。

换句话说：买得越多，中奖次数确实会变多，但亏损的期望只会等比放大——把注数放大 135 倍，投入放大 135 倍，期望回报也只放大 135 倍，比例纹丝不动（约 37.0%）。这就是"预测悖论"：即使一个人在选号上真有 1% 的优势（已经比本页检验过的所有策略都强），他也无法把负期望翻正——因为需要的优势量级是成百倍，而不是百分之几。

数据与方法

历史开奖数据来自 gudaoxuri/lottery_history（GitHub 公开仓库，描述为"彩票历史数据收集器"，由 GitHub Actions 每日自动更新），当前版本共 252 期（25005 ~ 26105）。该仓库已通过 GitHub API 核实存在且持续更新；本地数据与该仓库已做逐期逐号交叉核对（251 期全部一致，0 处不符），最新一期另用第二个独立来源复核过——完整记录见下方"数据来源核实记录"一节，那里也写明了本站曾经在这个问题上写错过什么。

回测采用 Walk-Forward 滚动预测：预测第 t+1 期时，策略只能看到第 1~t 期的数据，绝不使用未来信息。本版本 minTrainSize = 100，即前 100 期只作为初始训练数据，从第 101 期开始才正式计入回测成绩，实际参与评分的有 152 期。

随机基准和蒙特卡洛模拟都使用「期号 + 策略名」做种子的伪随机数，保证同一份数据永远得到同一份排行榜——回测模式下完全不使用 Math.random()。

本次一共同时检验了 3 个策略。检验的策略越多，就越容易"碰巧"挑出一个看起来不错的——哪怕数据完全是随机的。所以本站的"是否显著"一律用 Benjamini–Hochberg FDR 校正后的 q 值判定，而不是原始 p 值：随机基准：原始 p = 1.0000 → FDR 校正后 q = 1.0000；热号：原始 p = 0.1162 → FDR 校正后 q = 0.3485；冷号：原始 p = 0.3989 → FDR 校正后 q = 0.5984。

校正后没有任何策略达到显著，而且原始 p 值本来也不显著。

「无证据」是什么意思：不是数据不够，是数据已经够说明"没有大优势"

页面上的证据等级写着 无证据 时，很容易被读成"数据还太少，等攒够了再说"。这是完全反的，所以这一节用数字把它讲清楚。两种标签的含义截然不同：

证据等级什么时候出现它的真实含义
样本量不足该段期数少于 100 期（例如当前盲测集只有 31 期）数据确实太少，什么结论都不能下——这是"再等等看"唯一成立的情况
无证据期数足够（≥100 期），但置信区间覆盖了理论期望数据已经足够，结论就是"没有可检出的差异"。不是"还不知道"，而是"已经知道没有大的"

下面是"已经知道没有大的"这句话的量化版本。以目前检验过的热号策略为例（它是三个策略里表现最好的一个）：

问题答案怎么理解
我们现在这把"尺子"能分辨多细的差别？ ±0.2581 在 152 期、80% 功效下，任何每期多命中约 0.2581 个红球以上的真实优势，都会被我们检出来。比这更小的优势则淹没在噪声里。
实测到的差异有多大？ +0.1447 热号策略平均每期比随机基准多命中 0.1447 个红球——比我们这把尺子的分辨力还小，所以它落在"测不出来"的区间里。
这个差异最多能有多大？ [-0.0358, +0.3253] 95% 置信区间跨过 0（含负值），意味着"热号其实略差于随机"也完全说得通。即使乐观取上界，真实优势也不会超过约 +0.33 个红球/期。
那多攒点数据是不是就能确认了？ 约需 484 期 要把它坐实到统计显著，需要约 484 期（现在 152 期，约相当于再等 3.2 年）。
就算把它坐实了，值多少钱？ +0.13 元 / 注 把这点优势换算成奖金：命中 ≥4 红（四等奖及以上的必要条件）的概率从 0.4901% 升到 0.5551%，每注期望回报增加约 0.13 元——而每注成本是 2 元，单注期望回报本身只有 0.74~0.99 元。

所以"无证据"的正确读法是：数据已经足够，足以排除"存在较大优势"这个可能。剩下能被塞进这个区间的优势，小到连一毛三分钱都不值。继续攒数据当然可以，但它的意义是"把区间收得更窄"，不是"等一个好消息出现"。

顺便说明一个常见误解：如果哪天真的检出了显著优势，那才更需要警惕。因为在"每期独立等概率"这个前提下，长期的正确结果本来就是"没有差异"；一旦出现显著，优先怀疑的是数据、代码或统计口径出了问题，而不是"终于找到规律了"。这也是本站把"数据指纹 + 奖级全枚举自检 + 抽样核对表"放在同一页的原因。

以上数字全部是解析解（不依赖模拟）：标准误 = 配对差值标准差 ÷ √期数；最小可检出效应 = (1.96 + 0.84) × 标准误（80% 功效、双侧 5%）；所需期数 = ((1.96 + 0.84) × 标准差 ÷ 观测差异)²；金额换算用精确超几何概率（不是二项近似——第一版用近似时把 P(≥4红) 算高了 2.45 倍，已修正为精确值）。计算过程写在 src/build.js 的 buildEvidencePowerAnalysis 里。

这一版做了什么、还没做什么

当前已完成：V1（"我的策略"权重滑块 + 资金曲线）、V4 第零步（概率表与预测悖论、证据等级标注、数据指纹与核对表）、V4 第 1~4 层（数字体检、遗漏分布、形态诊断，以及本页最顶部的"下一期观测"），以及开奖后自动更新管道（GitHub Actions 定时抓取 → 交叉核对 → 硬校验 → 重算 → 生成页面 → 冒烟测试 → 工作流校验 → 合规审计 → 提交，任一门禁失败即不发布）。

关于顶部那个"下一期观测"区块，需要特别说明它的性质：它给出的是三组参数化规则 + 一组纯随机对照，不是预测结论。方案第十七节把预测功能拆成五层并规定：必须等证据等级、概率表、随机对照三样东西都能正常展示之后，"下一期观测"才允许上线——否则它只会变成一个看起来更专业的选号器。现在这三样都已就位，它才被放到最顶部。反过来也成立：如果哪天为了页面好看而把随机对照组或证据等级拿掉，这个区块就必须一起下线。

还没有做的，留给下一版：

  • 数据源这一条已经解决了，但还有一个缺口——仓库真实存在（gudaoxuri/lottery_history，GitHub Actions 每日更新），本地数据与上游逐期逐号核对 0 处不符，新增期另经官方开奖公告双源复核。缺口是：历史 252 期仍属单一来源，通过了内部自洽校验，但没有逐期与官方比对。
  • 资金模拟器参数化（初始本金 / 每期注数可调）、传播素材导出（擂台图 / 收敛曲线静态图片）
  • AI 战报（先用模板文案，暂不接入任何模型）
  • 大乐透等第二种彩票、Agent Skill 接口

关于"自动更新"为什么曾经失败过一次：工作流最初把 cron 的星期写成了 7（cron 合法域是 0~6），GitHub 因此在校验阶段拒绝解析整份文件，症状是"0 个 job、failure、无日志"，完全不像 cron 的问题。现已修复，并新增了工作流规则级校验与排程语义校验两道门禁防止复发——完整记录见 README 与方案 17.13。

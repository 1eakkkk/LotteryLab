# 随机数打脸实验室 · 双色球概率实验室（V1 + 安全防线）

> 任何策略，在没有通过盲测之前，都不准自称"有效"。

用真实开奖数据持续检验"选号策略是否真的比随机数强"的公开实验平台。**不做**号码预测工具，**只做**统计与算法科普实验。首页 `public/index.html` 明确声明：不提供售彩、代购、充值、返利等服务；彩票开奖是独立随机事件，历史数据不影响未来结果。

项目主线是方案里 **V0.5 → V1** 的迭代：V0 把"回测引擎是否算对"这件最不能返工的事做扎实；V0.5 把"开发集成绩"和"盲测成绩"第一次严格分开；V1 在此基础上加了"我的策略"权重滑块，把"开发集/盲测集分离"从一张静态的表格变成用户可以亲手拖动、亲手体验"数据窥探是什么感觉"的交互——这是方案第五节第 6 条一直悬而未决的功能，因为在 V0/V0.5 里三个基线策略都没有可调参数，这次真正派上了用场。

**新增（V4 第零步，方案第十七节 17.5）**：把"绝对不能做"从文档里的一句话，变成会让构建失败的可执行检查；并把方案 17.3 第 5 层（命中概率表 / 预测悖论）与 17.5 L3（统计层防线）真正做进页面。这一版**没有**加"预测下一期号码"的界面，而且这是有意为之——理由见页面末尾那一节，以及方案 17.6 的版本排序。

## 开奖后自动更新（本次新增）

双色球固定在**周二 / 周四 / 周日**开奖（用数据里最近 40 期的星期分布可验证：13/14/13）。两条自动更新路径，任一门禁失败就不发布：

### 路径一：GitHub Actions（不用管，开奖后自己跑）

`.github/workflows/update-lottery.yml`，按开奖时间排了三个窗口（UTC）：

| 触发时间（北京） | 用途 |
|---|---|
| 周二/周四/周日 21:40 | 开奖号码公布后 |
| 次日 00:00 | 上游仓库的写入时间实测在次日早上，这个窗口才是真正拿到新数据的时候 |
| 次日 08:40 | 上游刚更新完，兜底一次 |
| 周三/周五/周六也各排一次 | 多余的空跑只会得出"没有新期"并立即退出，成本几乎为零，但能覆盖临时加奖、数据补录、上游延迟 |

流程：抓取 → 逐期交叉核对 → **数据硬校验** → 重算回测 → 重新生成页面 → **冒烟测试** → **工作流规则校验** → **合规审计** → 提交推送。任一步失败即中止，**不提交、不发布**。也可以在 Actions 页面手动点一次（`workflow_dispatch`）。

**一次真实故障值得记在这里**：这份工作流最初把 cron 的星期写成了 `2,4,7`（想用 7 表示周日）。cron 的星期范围是 **0~6，没有 7**，GitHub 因此在**校验阶段就拒绝解析整份文件**。它的症状完全不像 cron 的问题——workflow 列表里的 name 退化成文件路径、每次 push 都产生一条运行记录但 **0 个 job**、状态 failure、点进去没有任何日志、邮件只说 "No jobs were run"，而**本地任何 YAML 解析器都会放行**（"7" 是合法 YAML，只是非法 cron）。排查方向一度跑偏到权限、账单、编码上。

修好之后顺带发现第二处独立错误：次日窗口原本写的是周一/三/五，而开奖日是周二/周四/周日，次日应为**周三/周五/周一**——整个窗口错开了一天。

为此新增了 `scripts/lint-workflows.js`（用 actionlint 做 GitHub 规则级校验），并给工作流加了 `push` 触发（用 `paths` 限制范围）——因为**定时任务无法即时验证**，改了配置要等下一个开奖窗口才知道有没有生效；有了 push 触发，配置错误当天就会暴露（本次故障正是靠它才被立刻发现）。

两个防御点值得单独说：
- **没有新期时，若数据文件却发生了变化，直接失败**——这不该发生，说明有 bug；
- **抓完之后会核对最新期号有没有真的变化**，防止"跑完了但其实什么都没抓到"这种静默失败。

## V4 第 1~3 层：数字体检 / 遗漏分布 / 形态诊断（本次新增）

方案 17.3 的前三层，全部做成了可交互的工具（点号码看详情、输入号码做诊断）：

- **数字体检**：33 个红球 + 16 个蓝球，每个号码的出现次数、理论期望、**95% 置信区间**、最近 10/30/50/100 期表现。置信区间用 **Wilson 区间**而不是常见的正态近似——因为正态近似在样本量小或比例接近 0/1 时会算出负数边界，页面上一旦出现"−3% 的出现率"这种数字，整页的可信度就没了。
- **遗漏分布**：点任意号码，看到它当前遗漏多久、历史最长遗漏、以及**这么长的遗漏在整份数据里本来该出现多少次**。这是正面回答那句"这个号该出了吧"：当前遗漏最长的红球 32 已 19 期没出，单看概率确实很小，但 33 个号码 × 252 期 = 8316 次机会下，这种长度的遗漏**本来就会出现约 183 次**。人只看了概率很小，没看机会有多少次。
- **形态诊断**：输入任意 6 个红球（或点"生成一组演示号码"），给出奇偶比 / 大小比 / 三区分布 / 连号 / 和值，以及**关键是最后一列**——有多少组号码和它"长得一样"。形态稀有 ≠ 更容易中奖。

### 这一层最重要的一个"防误读装置"

实测这份数据里有 **2 个红球**（24 偏多、26 偏少）的出现次数落在 95% 区间之外。任何预测网站到这里就该喊"发现异常号码"了。所以我们用蒙特卡洛算了纯随机数据的基线：

> 在 95% 水平上对 33 个号码各做一次检验，**即使开奖完全随机**，平均也会有 **1.793** 个号码落到区间外（理论值 1.65 个）；模拟 2000 次纯随机数据，出现"至少 2 个号码偏离"的概率高达 **56.2%**。

也就是说，**这个"发现"是完全随机情况下最正常的结果之一**。这就是多重比较陷阱：检验次数越多，"碰巧越界"的号码就越多，而只看那一个越界的号码是看不见这回事的。这个基线现在和体检结果并排显示在页面上——不写它，读者一定会把它读成"发现了规律"。

### 新脚本：`scripts/smoke-test-client.js`

这是本次新增的**第五道门禁**，补的是一个真实存在的缺口：页面里那三个工具的代码是**内联进 HTML** 的，平时没有任何东西会执行它——写错一个变量名，构建照样全绿、审计照样通过，而用户点下去什么都没发生。

这个脚本用一段极简 DOM 桩（无第三方依赖）把页面里的 `<script>` 抽出来真跑一遍，然后模拟"点 17 号""点诊断按钮""点生成一组"，检查渲染出来的内容对不对。共 25 项检查。

**它不是白加的——第一次跑就抓到了一个真 bug**：`window.LotteryTools` 没有挂上（`var LotteryTools = ...` 在脚本顶层创建的全局绑定，和执行环境里读 `window.LotteryTools` 并不总是同一个东西），三个工具在真实浏览器里会**全部静默失效**，而构建和审计全绿。已修复，并把这条教训写进了 `src/number-health.js` 的注释里。

## V4 第零步：安全底线落成代码 + 预测悖论上线

四件事：**两道门禁**（跑不过去）、**一层统计口径**（证据等级 + FDR 校正）、**一块零风险的新内容**（概率表与预测悖论，全部由组合数算出）、**一份数据自证**（指纹与抽样核对表）。

两道门禁，任一失败即非零退出，页面视为未产出：

### 1. `scripts/audit-safety.js` —— L1 合规红线层（7 项检查）

| 检查项 | 检什么 | 判定 |
|---|---|---|
| 违禁话术 | 35 个违规词（售彩/支付/承诺/权威四组）+ 4 条"号码交付"正则 | 命中即 fail |
| 交易类交互 | 无 `<form>`、`<input>` 只允许滑块/勾选、按钮文本无购买类动作 | 命中即 fail |
| 外部链接 | 页面自包含，不得有任何第三方购彩平台链接 | 命中即 fail |
| 声明完整性 | 必须同时存在"不提供售彩…"、"独立随机事件"、"不构成购彩建议"三段声明 | 缺失即 fail |
| 脚本注入 | 构建产物必须真的内联了 `my-strategy-client.js`（探针从源码动态提取） | 缺失即 fail |
| 确定性 | 回测路径不得出现裸 `Math.random()`（注释、页面文案、交互层按规则豁免） | 命中即 fail |
| 数字出处 | 页面上的百分比必须能在 `report.json` 里找到来源（已排除 CSS 样式值） | 仅警告 |

**关于违禁词检查的设计**：它不是简单关键词黑名单，而是**上下文感知**的。因为合规声明本身必然包含"售彩、代购、充值、返利"这些词（"不提供售彩、代购、充值、返利等任何服务"），简单黑名单会把最正确的那句话判成违规，最后逼着维护者把检查关掉——那才是这类脚本最坏的结局。所以只有落在"否定语境"（前 30 字内出现"不提供/禁止/不做/不构成"等）或"免责声明句/段内"的命中才放行。

### 2. `scripts/verify-data.js` —— L2 数据层防线（3 项硬校验 + 分布检验）

**硬校验（失败即停线，脏数据不许进回测管线）：**

- 格式/范围/顺序：期号唯一且严格递增、日期递增、红球 6 个互异且升序、蓝球 01~16、`source`/`fetched_at` 齐全；
- **奖级规则全枚举自检**：把 (0~6 红命中) × (蓝中/不中) 共 **14 种情况**全部跑一遍，逐条对照官方奖级表（含固定奖金金额）。这条最有价值——它证明的不是"数据对不对"，而是"我们算奖级的代码对不对"；
- 组合层概率自检：总组合数 `C(33,6)×16 = 17,721,088`，各奖级组合数合计 1,188,988，中奖概率 6.7095%，一等奖组合数必须为 1。

**软校验（输出报告，不阻断，但必须在页面明示）：**

- 红球频次分布：卡方统计量 **36.45**，蒙特卡洛 p = **0.1370**（2000 次模拟）——与"每期等概率"一致；
- 蓝球频次分布：卡方统计量 **9.40**，蒙特卡洛 p = **0.5205**——与"每期等概率"一致；
- **可复现性自检**：同一个卡方检验重复运行必须得到完全相同的 p 值（实测三次连跑逐位一致）；
- 数据指纹（SHA-256）：`af15e734a24cfba4…`，让"这份排行榜是拿哪份数据算的"变成可验证的，而不是靠信任；
- **抽样核对表**：最早 5 期 + 最近 5 期的完整号码，任何人都能拿去官方渠道逐条核对。

> 用蒙特卡洛而不是查卡方临界值表，是为了不在项目里塞一张"看起来有出处"的表，也不依赖近似公式：做法是在"每期等概率"的零假设下模拟同样规模的数据集，看真实数据的卡方统计量落在模拟分布的哪个位置。它回答的不是"彩票是不是随机的"，而是"**这份数据内部有没有表现出不该有的规律**"。
>
> **这个脚本不能证明什么（必须说清楚）**：它只能证明这份数据**内部自洽**，**不能证明数据来自官方**。数据来源是否真实，只能靠人工核对官方渠道或多数据源交叉比对。在换成可核实数据源之前，这条限制不能靠"校验通过"来掩盖。

### 3. L3 统计层：证据等级 + FDR 多重比较校正（本次新增）

把"能不能算有效"从一句人工写的免责声明，变成**由构建脚本自动推导**的结论字段：

- **证据等级**（对外唯一结论字段）：`样本量不足 / 无证据 / 弱证据 / 中等证据`，由样本量、置信区间是否覆盖理论期望、FDR 校正后的 q 值三条规则自动判定，**没有人工覆盖入口**。当前数据下的实测结果：

  | 数据段 | 随机基准 | 热号 | 冷号 |
  |---|---|---|---|
  | 整体（151 期） | 无证据 | 无证据 | 无证据 |
  | 开发集（121 期） | 无证据 | 无证据 | 无证据 |
  | 盲测集（30 期） | 样本量不足 | 样本量不足 | 样本量不足 |

  值得注意：热号均命中 1.1987、跑赢 93.9% 的随机策略，看起来相当亮眼——但它的 95% 置信区间是 [1.0621, 1.3353]，**覆盖了理论期望 1.0909**，所以证据等级是"无证据"，不是"弱证据"、更不是"有效"。这正是这一层存在的意义：**它不看数字好不好看，只看区间盖没盖住期望。**

- **FDR 校正**（Benjamini–Hochberg）：本次同时检验 3 个策略，原始 p 值与校正后 q 值的实测对比：随机基准 1.0000→1.0000、热号 0.1330→0.3990、冷号 0.3594→0.5391。`is_significant` 字段的口径已改为**校正后 q < 0.05**，原始 p 值保留在 `p_value_raw` 里备查。理由写在 `src/build.js` 的注释里：检验的策略越多，就越容易"碰巧"挑出一个好看的，不做校正等于在用户端重演一遍数据窥探。

### 4. 页面新增：命中概率表 / 预测悖论 / 数据核对（本次新增）

这一整块的所有数字都来自 `data/verification.json`，而其中的概率是 `verify-data.js` 用组合数 `C(33,6)` 精确算出来的，**没有任何硬编码的经验数字**（审计脚本会检查这一点）：

- **命中概率表**：总组合数 `C(33,6) × 16 = 17,721,088`，六档奖级各自的组合数、概率、约等于多少分之一，全部可复算；合计中奖概率 **6.7095%**（约 14.9 注里有 1 注能中任意奖级）。
- **预测悖论**：单注期望回报（固定奖级 **0.4863** 元 / 低档浮动估算 **0.7402** 元 / 中档 **0.9942** 元，成本 2 元）→ 每期买 135 注（投入 270 元）才能把期望回报凑到 100 元，而亏损比例和只买 1 注时**完全相同**。结论：即使真有 1% 的选号优势也翻不正负期望，因为需要的优势量级是成百倍。
- **形态过滤器演示**：加四个"最专业"的过滤条件（3奇3偶 / 不带连号 / 和值 90~115 / 三区 2:2:2），红球组合从 **1,107,568** 组降到 **23,109** 组（剩下 2.09%，"精选"了 47.9 倍）——**但概率没有变**。你改变的只是"把钱押在哪些组合上"。
- **数据来源核对**：硬校验清单、分布检验结果、抽样核对表、SHA-256 数据指纹全部上页。

## V1 这一版新做了什么


- **"我的策略"权重滑块**（方案第五节第6条，README 上一版排在"还没做的"第一条，这一版补上）：
  - 三个滑块：**热号倾向 / 冷号倾向 / 随机扰动**，对应打分公式 `score = hot×热号频率 + cold×冷号遗漏 + random×确定性噪声`。红球取分数最高的 6 个，蓝球取分数最高的 1 个——纯前端浏览器 JS 实时计算，不需要服务器、不需要联网。
  - 噪声项不是裸 `Math.random()`，而是「期号 + runId」做种子的伪随机数：同一组权重 + 同一份历史数据，永远得到同一组号码、同一个回测成绩，拖动滑块看到的变化只反映权重本身，不掺杂"手气"噪声。
  - **刻意拆成两个数字，互不干扰**：拖滑块时始终可见的是"历史回测成绩（开发集）"，明确标注"仅供娱乐，不作为策略有效性证据"；"盲测成绩"默认隐藏，要点按钮才揭晓，且**换一组权重后之前揭晓的盲测结果会自动作废**（必须重新点击），防止用户拿着上一组权重的盲测数字误当成当前权重的结果。
  - 用浏览器控制台 + Node 双端交叉验证过：同一组权重下，浏览器端算出的开发集/盲测集均命中数和 `node src/build.js` 里 `weightedStrategy` 走 `walkForwardBacktest` 算出来的数字完全一致（本版本验证组：热50/冷20/随机30 → 开发集 1.1074、盲测集 1.4333，两边分毫不差）。
  - 新增 `src/strategies.js` 里的 `weightedStrategy`，以及给浏览器用的等价实现 `src/my-strategy-client.js`（因为页面要求自包含、双击即可打开、不能用 Node 的 `require()`，这份是手写的无 CommonJS 版本，逻辑改动需要两边同步改）。

## 如何重新运行

需要 Node.js（开发时用的是 v22）。

```bash
node scripts/fetch-data.js     # 【门禁】抓取上游 + 逐期交叉核对（--apply 才写入，自动备份）
node scripts/prepare-data.js   # 清洗原始数据 -> data/ssq.json
node scripts/verify-data.js    # 【门禁】数据硬校验 -> data/verification.json（失败则停线）
node src/build.js              # 跑回测 + 蒙特卡洛 + 数字体检/遗漏/形态数据
node src/build-site.js         # 生成 public/index.html
node scripts/smoke-test-client.js  # 【门禁】模拟浏览器点击，验证交互真的能用
node scripts/audit-safety.js   # 【门禁】合规审计（失败则页面视为未产出）
```

七步跑完后直接打开 `public/index.html` 即可，不需要任何服务器或网络连接。或者直接一条命令：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\update.ps1
```

**注意第 1、3、6、7 步不是"建议"**：它们就是方案第十七节说的那几道门禁。跳过它们虽然还能生成页面，但等于把安全底线关掉跑——那样做出来的东西不能发布。接 CI 时必须把这几步一起串进去，否则自动化会绕过防线（`.github/workflows/update-lottery.yml` 已经串好了）。Cloudflare Pages 的构建命令相应地应写成：

```
node scripts/prepare-data.js && node scripts/verify-data.js && node src/build.js && node src/build-site.js && node scripts/smoke-test-client.js && node scripts/audit-safety.js
```


**关于盲测集边界的重要提醒**：`src/build.js` 里的 `VALIDATION_START_PERIOD`（26045）和 `BLIND_TEST_START_PERIOD`（26075）是这一版**手动写死**的常量。以后新增开奖数据、重新跑 `node src/build.js` 时，**不要**把这两个常量改成"当前数据的百分之多少"重新算一遍——那样会让盲测集随数据增长不断后移，变成一个名不副实的"最近窗口"。正确做法是让这两个常量保持不动，新增的期数会自动累积进盲测集（从当前 30 期慢慢变多）。只有在未来某个版本里**有意识地**决定"重新封存一批更大的盲测集"时，才应该修改这两个常量，并且要在这份 README 和发布记录里明确写清楚原因。

## 数据来源说明（已核实，并保留一次更正记录）

> **本站曾经写错这件事，这里保留痕迹，不删。** 更早版本的 README 与页面上写着："`gudaoxuri/lottery_history` 这个当前唯一数据源在公开搜索里没能找到对应仓库，无法确认它是否真实存在、是否还在维护。" **这个结论是错的。**

**实际情况（2026-09-13 核实）：**

| 核实项 | 方法 | 结果 |
|---|---|---|
| 仓库是否存在 | GitHub REST API `GET /repos/gudaoxuri/lottery_history` | **HTTP 200**，公开、未归档，TypeScript 项目，描述为"彩票历史数据收集器" |
| 是否还在维护 | 查询最近提交 | **最近一次数据更新提交为 2026-09-13**（GitHub Actions 每日自动更新） |
| 数据格式 | 拉取 `data/ssq.json` | 与本地 `ssq_source.json` 字段完全一致（`issueNumber`/`redBalls`/`blueBall`/`drawDate`） |
| 逐期交叉核对 | 本地 251 期 vs 上游逐期逐号 | **251 期全部一致，0 处号码或日期不符**；本地多出而上游查不到的期数 0 |
| 新增期双源核对 | 上游新增的 26105 期 vs 第二个独立来源 | 金华日报数字报《中国福利彩票开奖公告（第2026105期）》：红球 30 15 4 2 14 13、蓝球 8，**逐位一致** |
| 公告内部算术自检 | 用公告自身的销售额与六等奖注数复算 | 全国销售总额 333,874,688 元（合 166,937,344 注），六等奖 14,332,306 注占 8.5854%，与奖级规则量级一致（不依赖任何第三方） |

`scripts/fetch-data.js` 的流程：抓取上游（3 次重试）→ 双方各自做形状校验 → **逐期逐号交叉核对** → 新增期与第二来源比对 → 全部通过才写回，写入前自动备份。**两个来源对同一期给出不同号码时脚本直接报警停线，绝不"随便挑一个继续跑"**（方案第六节：抓错数据不被发现，比抓不到数据要恐怖得多）。

**仍然做不到的事（继续挂在明处）**：251 期历史数据是**单一来源**，它通过了内部自洽校验、并有抽样核对表支撑，但**没有逐期与官方比对**。自动校验只能证明数据内部自洽，不能证明它逐期都对。

## 如何部署（三选一，都是免费的静态托管）

项目现在的产物是**一个自包含的 `index.html` 文件**（所有数据、图表、"我的策略"交互全部写死在文件里），部署本质上就是"把这一个文件放到一个能提供 HTTPS 访问的地方"，不需要数据库、不需要服务器常驻进程。三种方式按推荐程度排序：

### 方式一：Cloudflare Pages（方案里指定的目标平台，推荐）

**A. 不用 Git，直接拖拽上传（最快，几分钟搞定）**

1. 打开 https://dash.cloudflare.com/ → 左侧菜单选择 **Workers 和 Pages** → **创建应用程序** → **Pages** 标签页 → **上传资源**。
2. 给项目起个名字（比如 `lottery-lab`），点击继续。
3. 把 `public/` 文件夹**里面的内容**（也就是那个 `index.html`）拖进上传框——注意是上传 `public` 文件夹里的文件，不是上传整个项目压缩包。
4. 点击部署，等几十秒。Cloudflare 会给你一个形如 `https://lottery-lab-xxx.pages.dev` 的网址，直接能访问。
5. 以后每次改完代码、重新跑完三步构建脚本，回到这个项目页面，用同样的方式再上传一次 `public/index.html` 就能更新（会覆盖旧版本，Cloudflare 自动保留历史版本，出问题可以一键回滚）。

**B. 连 GitHub 仓库，自动部署（适合你打算长期维护、以后接 GitHub Actions 自动化的话）**

1. 先把整个项目推到一个 GitHub 仓库（见下方"顺手学一下 Git/GitHub"）。
2. Cloudflare Pages → 创建应用程序 → Pages → **连接到 Git**，选中你的仓库。
3. 构建配置填：
   - **构建命令**：`node scripts/prepare-data.js && node src/build.js && node src/build-site.js`
   - **构建输出目录**：`public`
4. 保存后，以后每次 `git push`，Cloudflare 都会自动重新跑这三步构建脚本、自动发布——这正是方案里"V1.5 自动化管道"想要的效果的前半段（后半段是让 GitHub Actions 自动抓新数据后自动 push，这部分还没做）。

### 方式二：GitHub Pages（如果你已经有 GitHub 账号，不想额外注册 Cloudflare）

1. 把项目推到一个 GitHub 仓库（比如仓库名 `lottery-lab`）。
2. 仓库设置 → **Settings** → **Pages**。
3. **Source** 选择 `Deploy from a branch`，分支选 `main`，目录选 `/ (root)`——这也是为什么项目根目录也放了一份和 `public/index.html` 内容相同的 `index.html`（GitHub Pages 的 root 模式只认根目录的 `index.html`，认不到 `public/` 子目录，除非你把目录改成 `/docs` 并把内容放进 `docs/`）。
4. 保存后一两分钟，访问 `https://<你的用户名>.github.io/lottery-lab/` 即可。
5. 以后重新构建后，记得**同时更新根目录的 `index.html` 和 `public/index.html`**（内容应保持一致），再 `git push`。

### 方式三：本地直接打开，不部署（临时看看效果）

不需要任何账号、任何网络，直接双击 `public/index.html` 用浏览器打开就行——"我的策略"滑块也能正常工作，因为所有计算都在浏览器本地完成。缺点是别人没法通过链接访问，只适合你自己验证效果。

### 顺手学一下：怎么把项目推到 GitHub（如果你还没用过 Git）

如果你还没安装 Git 和建过 GitHub 仓库，最简单的路径：

1. 去 https://github.com/new 建一个新仓库（比如叫 `lottery-lab`），不用勾选"添加 README"（本地已经有了）。
2. 在项目根目录下打开终端，依次执行：
   ```bash
   git init
   git add .
   git commit -m "V1: 我的策略权重滑块"
   git branch -M main
   git remote add origin https://github.com/<你的用户名>/lottery-lab.git
   git push -u origin main
   ```
3. 之后每次改完代码、重新跑完三步构建脚本，只需要：
   ```bash
   git add .
   git commit -m "描述这次改了什么"
   git push
   ```
   如果用的是方式一的 B 选项或方式二，push 之后会自动触发重新部署，不需要再手动做别的事。

### 关于自定义域名

Cloudflare Pages 和 GitHub Pages 都支持免费绑定自己的域名（如果你有的话）：Cloudflare Pages 在项目的 **自定义域** 里添加即可；GitHub Pages 在仓库 Settings → Pages → **Custom domain** 里添加，并按提示在你的域名服务商那边加一条 CNAME 记录。两者都会自动帮你签发免费的 HTTPS 证书，不需要额外操作。
